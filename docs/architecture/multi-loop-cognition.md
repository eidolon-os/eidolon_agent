## 1. 问题不是「内核 vs 大脑」

`TurnEngine` 作为实时应答内核是正确的，并且应当继续是内核。真正的缺陷是
**这套系统只有一个时间预算**：首响 300ms / compile 250ms 是唯一的尺度，于是任何
放不进这个预算的能力都没有归属，最终表现为三种形态：

- 被删除：词法 triage（`939d468`，删得对，但没有替代物）
- 留了接缝不接线：`ContextCompiler(summary_provider=...)` 在 `bootstrap.py:472` 从未注入
- 定义了类型没有生产者：`TurnTrigger.PROACTIVE`、`SignalBus`/`PushSignal`、
  `Topics.memory_event_pattern()`、`sense.*`

「有配置无实现」不是疏忽的集合，而是**预算单一化的必然结果**。补的不是功能，是回路。

## 2. 四条回路

| 回路 | 时间尺度 | 是否用 LLM | 归属 | 现状 |
|---|---|---|---|---|
| **L0 反射** | <50ms | 否 | 现状：Channel 声学 + 打断裁决；agent 仅校验 typed committed-turn 并处理其后果（按播放边界截断）。**本提案不改动此归属** | 已有，且干净 |
| **L1 应答** | 250ms + LLM | 是 | `TurnEngine`（**保持现状**） | 已有，质量高 |
| **L2 轮间** | 秒级，用户在场 | 是（小预算） | 无 → 待建 | 缺失 |
| **L3 后台** | 分钟~小时，用户可离场 | 是（可批量） | 无 → 待建 | 缺失 |
| **L4 驱动** | 事件驱动 | 否（仲裁，不生成） | 无 → 待建 | 缺失 |

### L2 轮间回路（最被低估）

用户说完到下一句之间，KV 前缀是热的、persona 在手、本轮语义刚算过。这是做以下事情
最便宜的时刻：

- 写/更新滚动摘要（接 `summary_provider` 已有接缝）
- 预取下一轮可能需要的记忆（把召回从关键路径移出）
- 准备一句候选跟进，交给 L4 判断要不要说
- 按人格预生成本会话的等待话术候选池（见 `wait-speech-policy.md` §4）
- 维护会话级注意力（当前话题、未闭合的问题）

现有的 `speculative` 机制（`chat_servicer.py:175`、`turn.py:177`）本质上属于 L2，
但它今天由客户端驱动、无预算、无收益判断。

**为什么这条特别重要：** `domain/context/types.py:55` 记录的实测 —— RK3588 上一个
两位小数的 float 变化，因段序错误导致重读 113 token = 5.65s；改序后 27 token = 1.69s。
在这种算力上「能否提前算好」不是优化偏好，而是能否做出即时感的唯一杠杆。云模型上
L2/L3 是加分项；端侧算力上它们是必要条件。

### L3 后台回路

记忆巩固、persona 观察聚合、承诺生命周期镜像、长任务结果整合、日摘要、
**工具目录物化**（见 `tool-plane-mcp.md`）。可离线、可批量、可关停。

### L4 驱动回路（主动性仲裁器）

输入是**事件**：承诺到期（`eidolon.memory.event.*`）、在场变化（`sense.*`）、
长任务回流、日程。输出是「现在是否值得先开口」的裁决 + 抑制状态（免打扰、频次预算）。
经既有 `TurnTrigger.PROACTIVE` 与 `SubscribeProactive` 下发。

**它是仲裁器，不是生成器。** initiative 必须由证据驱动，不由状态驱动
（"我感到孤单所以找你说话"是操纵型留存的失效模式，也是监管重点）。

## 3. 让多回路不互相污染的四条不变量

这四条是「内核与大脑不冲突」能否成立的全部前提。

**I1 单向状态契约。** L1 只读慢回路已物化的状态，永不在热路径同步等待它们。
现有 memory fanout + durable outbox 已经是这个纪律，把它上升为回路级规则。

**I2 每条回路自带预算、SLO 与降级。** 慢回路超时是慢回路的事故，不允许变成 turn 的延迟。
**可验收：关停任意慢回路，L1 行为不回归。** 这是一条可写成测试的边界，也是 L2/L3
允许上线的前提。

**I3 慢回路产物必须落成带易变性等级的 typed segment。**
`SEGMENT_ORDER`（`context/types.py:68`）与 `volatility_rank` 就是这个原语：
摘要/固化结果归 `append_only` 或 `stable`，L2 的临场预判归 `volatile` 且靠后。
没有这条，多回路会把段序优化赚回的时间重新赔掉。

**I4 慢回路产物必须带来源与可撤销。** 这是生物类比**不适用**的地方：人脑固化错了
无人追责；伴侣把"你不喜欢你妹妹"固化进长期记忆，用户要带着这个错误生活。
provenance + 可撤销 + owner 可见是 L3 的准入条件，不是后续功能。

## 4. 类比会带偏的三处

1. **固化不免费。** 人反正要睡；LLM 巩固是每 owner 每天的真实成本，必须能证明价值，
   否则只是花钱生成听起来合理的摘要。L3 必须自带成本预算与效果度量。
2. **正确性要求不同。** 见 I4。
3. **不要建"驱动/情绪"生成器。** 见 L4。

## 5. 设计原则一句话

**不要让 turn 变聪明，要让 turn 的输入变聪明。**

`TurnEngine` 应保持为「物化状态 + 当前输入」的近似纯函数；"大脑"是内核加上另外三条
回路的合成体，而不是把认知塞进内核。

## 6. 对既有批次的影响

原方案里笼统的「慢回路」应按回路拆开，并调整顺序：

| 原 | 调整后 |
|---|---|
| P1 滚动摘要写入器 | 归 **L2**，仍在 P1（缓存热、成本低、收益直接） |
| P1 召回并发化/查询改写 | 归 L1（关键路径内），P1 不变 |
| P1 owner 偏好层 | 已部分落地（工作区 `ConversationPreferences` + RESPONSE_POLICY 段），剩余是持久化与热生效验收 |
| P2「慢回路运行时」 | 拆为 **L2 运行位**（P1 末）与 **L3 后台回路**（P2 首） |
| P2 主动性 | 归 **L4**，依赖 L3 的承诺镜像与 `sense.*` 接入 |
| P3 工具生态 | 目录物化归 **L3**，per-turn 选择归 **L1**（见 `tool-plane-mcp.md`） |

先做 I2 的验收测试（关停慢回路 L1 不回归），再允许任何慢回路进主干。
