# 等待话术（Wait Speech）：工具耗时未知时说什么

状态：设计方案（proposal），不是已实施变更。基线 `eidolon_agent@bfe685d`（2026-09-14 复核）。
配套：`multi-loop-cognition.md`（S 层预生成属 L2、延迟先验属 L3）、
`tool-plane-mcp.md`（`ToolSchema` 扩展字段）。

## 1. 现状

| 事实 | 证据 |
|---|---|
| 一轮最多一句，固定文案 `"稍等，我处理一下。"`，1.5s 后发 | `domain/agent/turn.py:82-88`（`ToolLatencyPolicy`）、`turn.py:415-445` |
| 人格只能整句覆盖一个字符串 | `_persona_phrase(ti, "slow_tool_hint", …)`（`turn.py:989`） |
| 快工具保持静默（正确） | 1.5s 门槛 + `slow_tool_hint_emitted` 单次闸 |
| 委派 coworker 的话术算**答案**内容，不算等待提示（正确区分） | `_tool_answer_announcement`（`turn.py:978`） |
| Channel 只让 `slow_tool_hint` 这一个非答案 role 进 TTS | `grpc_llm.py:474-489` |
| **Channel 按 role 去重**：同 role 的第二句被静默丢弃 | `grpc_llm.py:476-478` `spoken_preamble_roles.add(payload.role)` |
| 一旦发出即进入 TTS 流，无法撤回 | 作为 `ChatChunk.content` 送入 LiveKit |
| `enable_filler_phrases` 是死配置 | `settings.py:322`，除 settings 无引用 |
| 每个工具的 `latency_ms` 已经逐轮持久化（可用于建先验） | `ToolTrace` → turn row `timings.tool_trace` |

两个结构性约束必须先说清楚：

- **按 role 去重意味着「分级话术」今天做不出来。** 想说第二句就必须给它不同的 role
  （或把 Channel 的去重键改成 stage）。这是唯一的跨仓阻塞项。
- **发出即不可撤回。** 所以「先发再看要不要撤」的方案不成立；必须**发之前就判断值不值得发**。

另需核对：等待话术作为 `ChatChunk.content` 进入 LiveKit 的 assistant 消息，
而打断上下文重建会读 assistant `text_content`（`eidolon_channel/.../context/interrupted.py:95`），
因此等待话术可能污染打断后的上下文。机制上成立，未实测。

## 2. 五条原则

**P1 等待话术的职责是设定预期，不是填充静默。**
它要回答用户此刻真正的疑问：「它听见了吗」「它在干什么」「还要多久」。
`"稍等，我处理一下"` 三个都没回答，所以第三次听到就露馅。

**P2 自然度来自信息量，不来自措辞的花样。**
`"我查一下天气"` 比任何一种「稍等」的变体都自然，因为它是人真会说的话。
**动作命名是首选，通用填充是兜底。** 把力气花在生成更多"稍等"的说法上是错的方向。

**P3 分级，而不是一句。** 不同等待时长对应不同的通信行为（见 §3），
一句话不可能同时适配 1 秒和 30 秒。

**P4 短等待用非词汇确认，不用句子。**
人在 300–800ms 的空档发出的是 `"嗯——"`/`"好"`/一次吸气，不是完整句子。
**非词汇标记可以近乎无限重复而不显得套路，句子不行** —— 这是本方案里性价比最高的一条。

**P5 等完要收尾，且不许虚报。**
长等待结束后承接一句（"让你等了下"）是人和进度条的区别；
反过来，不许说「马上就好」除非先验支持，不许播报内部流程（harness 已明确禁止）。

## 3. 分级阶梯

| 阶段 | 触发 | 通信行为 | 示例 | role |
|---|---|---|---|---|
| **S0** | 0–600ms | 静默 | — | — |
| **S1** | 600ms–1.5s | 非词汇/最短确认 | "嗯——" / "好" | `wait_marker` |
| **S2** | 工具语义已知且先验 p50 >800ms → **立即** | 动作命名 | "我查一下天气" | `wait_action` |
| **S3** | 4–6s | 进行中 + 预期（**仅在有先验时给时间**） | "还在查，再几秒" | `wait_progress` |
| **S4** | >15s 或 p90 超阈值 | 提议改路径（转委派，**算答案内容**） | "这个有点久，我先记下，弄好告诉你？" | `answer` |

### 关键反转：不用固定延迟决定，用先验决定

现在的 1.5s 固定门槛对**通用填充**是对的，对**动作命名**是错的 ——
动作命名不是填充，它是人本来就会先说的那半句话，越早说越自然，而且它直接消灭了空档。

| 先验 | 策略 |
|---|---|
| p90 < 800ms | 全程静默，不发任何提示（今天已正确） |
| p50 ∈ [0.8s, 4s] | dispatch 瞬间发 **S2 动作命名**，不等 1.5s |
| p50 > 4s | 立即 S2 + 预期，随后 S3 升级，必要时 S4 转委派 |
| 无先验（冷启动/新工具） | 保守回落到今天的行为：600ms→S1，1.5s→S2，并记录本次耗时以建先验 |

先验由 L3 从 turn row 的 `tool_trace` 物化（per-tool p50/p90 或 EWMA），
热路径只读快照。这份先验同时给 `tool-plane-mcp.md` 的工具选择器提供成本信号。

**每轮至多 2 句口头等待**（S2 + 一次升级），加可选 S4。再多就是催promt。

## 4. 变化性：结构化，而非随机

随机抽句子仍然像套路，而且会和人格冲突。做法：

1. **槽位语法**：`{接续}{动作}{对象}{限定}` —— 例：`（好，）(我)(查一下)(天气)(，稍等)`。
   按「语义类 × 人格语域」各自维护槽位池。
2. **人格化池由 L2 每会话预生成**：会话开始或轮间空档，用一次 LLM 调用按当前人格生成
   每个语义类 3–5 句候选，校验（长度、不虚报进度、不承诺时间、不播报内部流程）后缓存。
   **热路径零成本、跨会话与跨人格自然不同、不存在硬编码字符串。**
   这是 `multi-loop-cognition.md` 里 L2 回路最直接的收益；生成不可用时回落静态池。
3. **确定性选择 + 抗重复**：`hash(turn_id)` 取模，排除会话内最近 K 次已用；
   池被用尽时**降级为非词汇标记，而不是重复句子**。
4. `ToolSchema` 增加 `action_phrase`（如 `"查天气"`），MCP 工具在**目录物化阶段**从
   description/annotations 推出并缓存，不在每轮推断。

## 5. 需要改的契约

**Agent 侧**

- 新增 `domain/dialogue_policy/wait_speech.py`：
  `WaitSpeechPolicy.plan(calls, priors, pools, session_state) -> list[WaitUtterance]`
  （`at_ms` / `role` / `text` / `stage`），纯函数、可测、可回放。
  把 `ToolLatencyPolicy` 的单文案降级为它的兜底路径。
- `ToolSchema` 增 `action_phrase`；`risk`/`tags` 复用 `tool-plane-mcp.md` 的扩展。
- L3 物化 `tool_latency_prior`（建议独立小表或快照，避免每次扫 turn row JSON）。
- `TurnTrace.wait_speech`：到达的最高 stage、用了哪条候选、用的先验、
  以及**发完后工具是否很快就返回了**（用于算 §6 的 precision）。
- 等待话术永不进 history / memory / 答案文本（今天的 hint 已符合，新阶段必须保持）。

**Channel 侧（跨仓，S1–S3 的前置条件）**

- 去重键从 `role` 改为 `stage`（或引入 §3 的四个 role），否则第二句被静默吞掉。
- 按 role 给韵律：等待类降能量、略快、句尾下沉；**非词汇标记优先用预置音频样本**
  （真人 `"嗯"` 比 TTS 念 `"嗯"` 自然得多，且延迟接近 0）。
- 等待话术不得进入喂给打断上下文重建的 assistant 文本（先核对 §1 末的怀疑）。
- 若等待话术仍在 TTS 队列未开口而答案已到，丢弃它 —— 需要它是**可取消的独立片段**，
  而不是内联在答案流里的文本。

## 6. 怎么验收（可测，不靠体感）

| 指标 | 定义 | 门槛方向 |
|---|---|---|
| `hint_precision` | 发出等待话术后，等待确实又持续 >1s 的比例 | 越高越好；低说明在乱插话 |
| `dead_air_p95` | 用户说完到首个音频输出 | 有上限 |
| `repeat_rate` | 同一会话内同一句等待话术复现率 | 接近 0 |
| `false_time_promise` | 无先验却给出时间承诺的次数 | 必须为 0 |
| `stage_ladder_ok` | 慢工具场景下 S1→S2→S3 是否按序到达且未被去重吞掉 | 契约测试 |

进现有基准体系：`app/benchmark/suites.py` 增一个慢工具场景族
（工具耗时 0.3s / 2s / 8s / 30s 四档），断言阶梯、不重复、不虚报、不播报内部流程。

## 7. 明确的反模式

- **千篇一律的"稍等，我处理一下"**（今天的默认值）。
- **随机轮盘**：忽长忽短忽正式忽随意，比固定一句更破坏人格一致性。
- **虚报进度或时间**："马上就好" / "还有 3 秒"（除非先验支持）。
- **播报内部流程**："正在调用天气工具" —— 违反 harness 策略，且立刻暴露机械感。
- **填满每个空档**：<600ms 的静默是正确的，不需要补。
- **把等待话术当答案存起来**：会污染历史、记忆和打断恢复。
