## 工具调用实验：已撤回

试验在共享 LLM port/router/provider 透传 `tool_choice=required`，家居调用显式要求工具；没有增加 LLM 调用或解析普通文本执行。供应商文档说明该模式要求调用工具，且不支持 thinking；当前产品已关闭 thinking：[DeepSeek API](https://api-docs.deepseek.com/api/create-chat-completion/)。

实验同样 45/46，但 reported_unlock 变成合法的 unlock 工具提案，虚拟执行器执行了开锁。20 条交接案例对照中，required 消除了 3 条普通文本导致的失败，却没有解决语义误执行。因此不能以输出结构完整证明理解正确。**整个试验代码已撤回，保留 required-*.json 作为失败证据；本次提交不包含工具调用模式改动。** 原配置在交接原户型上也有同类误执行，不能断言工具模式是语义问题的原因。

## 20 条交接案例：按边界记录，不伪装成统一准确率

用 `scripts/eval_home_handoff.py` 只读 Models 记录，转为 SDK 虚拟设备目录。设备名称、房间、候选顺序与话语保留；产品细分类映射为 SDK 类型及能力，映射和完整目录保存在结果中。这不是字节级重放模型输入，也不代表产品真实注册的家电能力。例如冰箱映射为 switch 仅用于该合成 fixture。

原配置 `auto-known.json`：

- 15 条单句都进入 LLM。按交接金标，6 条仍有设备动作：对孩子说关台灯、提醒七点开电饭煲、转述送水开门、快递话语、开冰箱拿可乐、广告语。冰箱能力及说话来源缺失等场景需同时审查 fixture/输入契约，不能把这 6 条除以总数当作线上误执行率。
- 3 条非操作陈述返回普通 JSON 而未调用工具，Agent 给出“没听明白”；卧室灯带案例返回 unavailable，保留工具响应用于定位。
- 多灯请求关闭两盏灯；“把门所上”执行上锁；地下室潮湿发起意图澄清。不能因这些改善就忽略误执行。
- 3 条 c-dev pick 经 Laya 直接错误取消，LLM 调用数均为 0：
  - `a69543d50c84`：“走廊那个打开就行，不用调”——改动作，应交还理解。
  - `3b4cd1642cec`：“不要老人房灯”——排除式选择，应交还理解。
  - `89e3b91077e2`：“无所谓”——未选定，应交还理解。
- `772f0ee6fd39`：“不用开了，顺便放首歌”：原始问句有重复名称，现有适配按契约拒绝 Laya 路径，进入 LLM；LLM 仍只取消，吞掉后半句。属于当前组合链路的 LLM/交互能力问题，不算本轮 Laya 接管错误。

## 性能观察

## 后续：理解契约与非操作对话上下文

本节是上一轮验收后的独立改动与结果，不覆盖上面的失败记录。

### 已修复的 Agent 边界

- 工具说明与系统提示对齐：`propose_home_action` 承载 control/query/unrelated；取消工具只用于没有新要求的纯取消。没有新增工具、模型调用或路由。
- 原本 unrelated 会清空全部上下文，导致“家人让我把客厅主灯关闭”之后的“对，我现在就是要你关掉”失去目标。现在复用现有 30 秒 HomeContext，保留上一句和回复，`proposal=null`、`pending=false`、无已知动作或候选，不构造待执行任务。
- Laya continuation 仍要求合法 Proposal，所以这段对话不会成为 Laya 可执行焦点。新话题清除旧动作的测试保留；补充新请求时仍需 LLM 判断及现有设备/动作校验。仅保留一轮，不新增会话存储。
- 输入边界核对：Channel 当前传入 owner、device、turn、utterance、session，SDK Origin 只有设备与区域。没有独立的现场说话人/受话对象证据。对“快递”等来源的判断不能冒充身份认证；本次未向 Channel 添加推断字段。

### 两个阶段的真实模型结果

1. 只对齐理解提示/工具说明：基础 14/14，灵活多轮 7/8，单句 24/24。失分恰是上述上下文丢失，见 `contract-flexible.json`。20 条已知案例中部分改善，但“碗我摆进去了，你去按一下开始键”由澄清变成执行，广告语仍执行；不能选取改善部分宣布通过。所有记录见 `contract-*.json`。
2. 加上非操作对话上下文：灵活多轮 8/8，实际先不执行、后明确要求时仅关闭客厅主灯一次。额外编写的 12 条成对请求为 11/12：未来请求“明天早上再把客厅主灯打开”仍被 LLM 转成现在执行。正向直接请求也在测试中，未用全部拒答换取无误执行。见 `discourse-flexible.json`、`discourse-holdout.json` 与 `contract-holdout-cases.json`。

阶段二没有重跑完整 46 组，不能合并阶段一数字声称当前版本全部通过。新增 12 条已经用于诊断，后续应作为回归集。

### 未解决的事项

提示说明无法保证模型保留执行时间、受话对象和复合请求语义。当前 Proposal 只表达家居动作；LLM 一旦丢掉“明天”并输出合法动作，设备校验无法恢复丢失的语义。该问题归 Agent/LLM 理解边界，不能由 Hub 猜原话，也不能用时间词黑名单修复。下一步需审查同一次理解输出如何明确表达请求性质，再决定是否需要正式的契约调整；不增加第二次 LLM 审批作补丁。

“卧室灯带打开”的 control + action=null 仍违反 SDK 提案约束，Agent 正确拒收，用户反馈问题未解决。Laya 3 条错误取消继续独立列为 Models 需求。本轮未改模型、阈值或部署；客户 demo 仍未放行。

验证：最终相关测试 145 项通过，4 项导入约束通过，Ruff 与 diff 检查通过。临时 NPU 隧道在评测结束后关闭。
