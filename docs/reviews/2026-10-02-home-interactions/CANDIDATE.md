# Agent 家居交互正确性候选

本候选基于 `c22ddd1`，分支 `codex/home-interaction-correctness`。承接原有日志、逐轮评测与 FakeExecutor 音量状态修正。原始 baseline / repeats / probes / backend-comparison / independent-witness 与原 provenance 文件均保留，哈希核对一致。部署状态：尚未部署。

## 设计与边界

### 目标与路由

- 在续接之前复用 `RulesInterpreter(require_complete=True)` 判断是否是完整独立指令，清空 origin 的房间偏置后取证。得到完整、resolved 的解释时直接调用既有单句解释器；两者不一致、低概率或服务异常时，保留实际上下文交给 LLM。
- 严格规则不能完整读取“再关闭电视”“把音箱打开”等句子。为此，c4 follow 的适用范围另外检查完整目录中的设备名称、用户别名、设备词、场景和房间引用。复用规则解释器现有最长匹配与噪声词处理；发现显式引用就退出 follow，由完整理解处理。
- 该检查仅限制旧焦点续接，不从关键词生成动作，也不把被否定、转述或改口中的名称视为执行授权。不增加设备名特判，不改变 c4 问题、选项或阈值。
- 上下文依赖且没有显式引用的单焦点仍走 follow；待选择时，完整且唯一的设备名称/别名若精确匹配已展示候选，直接选用原待执行动作；其他回答仍走现有 pick。名称匹配使用完整目录，否定、额外动作、同名歧义或候选之外的目标不能走这一确定性选择。follow 退出后只调用一次 LLM，没有固定的 follow → single → LLM 串行链。
- 这是对当前词法能识别的引用的边界，不是任意自然语言的目标语义证明。Models 对 c4 高概率错误的纠正仍有独立价值。

### 语义与提案

- 部分排除候选不能自动补选；剩一个也需肯定确认。全部候选被明确拒绝且无新请求时结束请求。
- 取消并提出新请求时处理新请求。非家居请求返回现有家居能力范围反馈，不接入陪伴 prompt / memory / TurnEngine。
- 改房间且省略设备类别时继承已有类别，在新房间查找同类设备；不把范围扩成该房间的全部设备。
- 多目标后的单数指代要求澄清，明确复数可操作全体。c4 当前未区分这一范围，因此多焦点 follow 暂交给完整理解。LLM 的结构化提案仍检查单数词法与多焦点的一致性，防止模型选一台或扩成全体；澄清保留当前动作供下一轮选择。
- Laya 与 LLM 共用现有数字解析，设备名称和别名内的数字先被排除。对只有一个可解析数值的绝对设置提案，模型给出的数值若与原话不一致则要求澄清，不允许模型擅自截到上限，也不自动把相对表达改成绝对值。多数字、复杂计算和其他表达仍由完整理解处理；这不是通用语义验证器。

### 本轮明确的支持限制

`Proposal` 仍只有一个共享 action。本轮不扩展 SDK、Hub 或第二套规划/执行系统。一句包含不同动作时请用户拆开，不宣称已经支持异构多动作。

完整理解提出 control 后，现有规则读取若已识别多个不同动作，则先澄清，防止模型只返回第一项；规则在消费数值前保留动作词，避免“打开并设为30”中的“设为”被数值读取吞掉。这个受限检查也可能对难以区分的改口要求澄清，不宣称覆盖所有复合句。

在当前目录上生成既有 `CommandPlan` 后，若多目标中有任一目标在执行前就拒绝该动作，整轮先澄清，不向 Hub 发送可执行的子集。真正执行后遇到离线、超时或部分失败仍如实返回 partial / unknown，不假装事务回滚。

越界数值的合法范围来自 SDK 的 `TRAIT_COMMANDS` / `DEVICE_TYPES`，在执行前提示范围并保留目标、等待新数值。没有新增能力范围表。

## 验证过程

所有候选评测使用固定 c4 `7b695ba8`（opi5max 现有 8771，经临时本机 18771 转发）与 `openai/deepseek-v4-flash`。执行只有 `SmartHomeCommand + SDK apartment + FakeExecutor`；没有 Hub 客户端、真实家电或共享服务重启。

- v1 原42组：41/42满足原预期；唯一差异是组合动作按支持限制澄清。原失败两轮复跑14/16，两个差异也是同一组合动作。原诊断8/8通过。
- v1 新18组自然改写：17/18通过。保留“拒绝全部候选后重复追问”的失败。
- v2 明确全部拒绝语义后，新18组为16/18；全部拒绝通过，但出现LLM单数指代扩为全体和150%被截为100%的实际虚拟执行。该失败不被后续成功覆盖。
- v3 校验阻止了单数扩为全体，但新改写仍16/18：用户明确选中音箱后LLM多问一次，以及同一设备两个动作只执行第一项。随后复用精确名称匹配，并修复原规则丢失设置动词的问题。
- v4 运行在单元测试发现该动词缺口后被停止，保留日志，不作为完整验收。v5整套已完成并满足声明边界，但发现共享SDK工作区出现另一个任务的v2改动，因此不作为固定依赖的最终证据。
- v6 使用冻结 Agent 源码、SDK `c375645` 的独立只读导出、固定 c4 和同一产品LLM。此轮原42组/重复/诊断满足声明边界，但新改写17/18：第一轮LLM不可用导致没有焦点，下一轮LLM猜测客厅灯。保留该服务失败及其后的错目标，不仅归咎于可用性。
- v7 增加无焦点单数指代检查；完整房间名称不等于设备身份。有已知待补全目标时仍可继续，缺失/取消/失败/过期后的无目标指代要求说明设备名称。最终汇总见 `candidate-summary.json`，依赖与源文件哈希见 `candidate-v7-provenance.json`。

原 `cases.json` 中异构多动作仍要求两项都执行，因此在原评分下仍计未达预期。`candidate-scope-cases.json` 单独声明当前支持边界，只对这一项改为零执行并澄清；不得把受限策略通过说成完成了原功能。

这批数据是发现问题后构造的开发/回归材料，复跑用于观察波动，不是独立统计测试集。Mac调用、SSH和FakeExecutor耗时不代表Korvo语音端到端时延。

本轮初始7次Laya请求发生传输错误；临时SSH输出7条远端连接拒绝，与初始请求的ReadError相符，随后恢复。7次均由LLM正确兜底。本任务未重启共享服务；没有足够证据判断远端不可用的根因。另有上述1次LLM不可用。因此原五轮的v7耗时全部包含LLM，不能拿它证明快路径时延。

v6在服务可用时，同样的合成“开音箱”为一次单句Laya、399ms、无LLM；v7该句因Laya传输失败转LLM、1062ms。两者均只代表各自的Mac/SSH/FakeExecutor样本。v7所有不调用LLM的73轮中位422ms、样本p95为463ms；调用LLM的120轮中位1529ms、样本p95为2134ms。没有以候选最好一次覆盖服务失败记录。

确定性边界已由390项测试和实际回归验证；排除候选、取消新请求与房间类别继承中的语义判断仍依赖LLM。不同动作组合是明确限制，并未完成原功能。SDK多动作契约与Models模型候选均未在本任务扩大或替换。当前仍不据此放行客户demo：还缺服务可用性问题排查、模型交接及固定版本部署后的Korvo端到端验收。

全部评测只使用FakeExecutor。临时18771转发已关闭；没有启动18772，也没有部署候选或执行真实家电。

## 剩余 demo 门槛

1. 独立 Models 候选需要交接固定 revision、校准与两后端验证结果；本候选没有训练模型或修改Models文件。
2. 明确接受首期共享动作边界；需要一轮异构多动作时，应另行评审 SDK 的提案表达与既有命令列表，不继续靠提示词假装支持。
3. 按 Ops 固定版本流程发布后，仍需复验 Owner/Companion/session、真实 ASR、Hub 回执与 Korvo 接收/绘制 ACK。本轮不据虚拟执行放行客户 demo。
4. LLM对排除、取消与房间继承仍有模型语义依赖；有限回归成功不是任意话语正确性的保证。
